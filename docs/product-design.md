# Global Weather Product Design

## 产品定位

Global Weather Atlas 是一个按天气反向选择旅行目的地的工具页。用户先选择地区、时间窗口、温度、天气、湿度和海拔偏好，再通过地图和结果列表找到未来几天更适合出行的城市。

## 当前范围

目前只实现一个工具页，支持中文和英文两个入口：

```text
/zh   # 中文工具页
/en   # 英文工具页
```

后续可以增加独立落地页，但工具页仍是产品第一屏，不把可用体验藏在营销页之后。

## 主要任务

| 任务 | 说明 |
| --- | --- |
| 旅行筛选 | 按未来 3/5/7/10/14 天筛选城市，展示匹配天数和平均温度 |
| 单日图层 | 选择某一天，在地图上查看气温、天气、降水、湿度、海拔和舒适度；区域着色、地图选择和视野框选规则见 `docs/map-region-coloring.md` |
| 地区聚焦 | 支持全球、大区、国家和中国省级筛选 |
| 城市详情 | 选中城市后展示未来 14 天温度、天气、湿度和降水 |
| 双语体验 | UI 控件、图例、结果摘要和城市名称支持中文/英文 |

旅行筛选和单日图层使用路径区分：`/{locale}/travel` 和 `/{locale}/daily`。筛选条件放在 query 中，便于刷新和分享；`region`、`days`、`date`、`layer`、`temp`、`weather`、`humidity`、`elevation` 都应能从 URL 恢复。

单日图层的 `date` 是当前地区可用日期里的实际本地自然日。不同地区因为时区和天气源返回窗口不同，可用日期集合的头尾可能不一样；用户切换地区时，界面按日期滑块的相对位置迁移，例如当前选第 3 天，切到新地区后也选新地区的第 3 天，并把新的实际 `date` 写回 URL。

## 地区选择 Spec

地区选择、地图区域点击、着色粒度和地图视野框选规则统一见 `docs/map-region-coloring.md`。产品文档只描述入口能力，不重复定义具体地区 key、行政层级和 bounds 规则。

## 旅行时间窗口 Spec

系统保留未来 14 天天气数据，但用户不一定在规划 14 天行程。旅行筛选的 `days` 表示本次旅行计划长度，支持 3、5、7、10、14 天；推荐分数、匹配天数、区域着色和结果排序都只使用从当前可用预报开始截取的这段窗口。

14 天是数据缓存上限，不是默认假设的旅行长度。短途旅行用户选择 3 天或 5 天时，城市只需要在短窗口内满足天气偏好；长途旅行用户选择 10 天或 14 天时，系统再按更长窗口计算稳定性。

## 视觉方向

界面是工具型数据工作区，不做 landing page 风格的 hero。地图占据主要视觉面积，筛选、结果和未来天气条围绕地图组织。色彩保持中性地图底色，搭配温度、天气、湿度和舒适度色带。

## 技术边界

当前实现是 `apps/web + apps/worker` 多运行单元项目：

```text
apps/web      # Astro + React，负责公开工具页和双语路由
apps/worker   # Node.js Worker，负责启动时初始化数据库和每日刷新天气
packages/*    # 只有 Web 和 Worker 真实共享的类型、天气码和 DB 访问
```

Web 只读 Postgres 中已整理的数据；Worker 写入 Postgres 并记录刷新状态。公开请求不直接调用天气供应商，也不在用户访问时现场刷新数据。
